# Working on this repo

Everything under `src/IncidentIo/Generated/` is generated by
[Kiota](https://github.com/microsoft/kiota). Don't edit it: the next release
overwrites it. Changes to the API surface come from the upstream OpenAPI schema.
Changes to the *shape* of the generated code come from
`scripts/prepare_spec.py`, which rewrites a copy of the schema before Kiota
reads it, and `scripts/rename_identifiers.py`, which renames identifiers in
Kiota's output.

Hand-written and safe to edit: `src/IncidentIo/IncidentIoClient.cs`, the
`.csproj` files, `tests/`, `scripts/`, the `Makefile`, `.github/`,
`README.md` and this file.

## Prerequisites

| Tool | Needed by | Notes |
| --- | --- | --- |
| .NET SDK 10 | everything | `global.json` pins the version |
| .NET 8 runtime | `make test` | the tests run on every target framework |
| Python 3 | `make generate` | runs `scripts/prepare_spec.py` |
| network | `make generate`, `make api-compat`, `make oasdiff` | Kiota is a dotnet tool restored from nuget.org |

Kiota itself needs no install: `make generate` runs `dotnet tool restore`,
which installs the version pinned in `.config/dotnet-tools.json`.

Without a local .NET install, the Makefile runs in the
`mcr.microsoft.com/dotnet/sdk:10.0` image once `make`, `python3` and the .NET 8
runtime are added to it.

## Targets

`make help` lists them. The ones that matter:

- `make generate`: rewrite the **committed** `openapi.json` into
  `build/openapi.prepared.json` and generate from that. Start here after
  changing anything in `scripts/`.
- `make test`: build with warnings as errors, pack, then run the tests on
  net8.0 and net10.0. This is what CI runs.
- `make oasdiff`: the schema gate that stops a release, runnable by hand.
- `make api-compat`: the C# API gate that stops a release. Before the first
  release there is no baseline on nuget.org, so it says so and passes.

## How a release happens

`.github/workflows/sync.yml`, hourly. When the live schema differs from the
committed one it regenerates, verifies, bumps the **minor** version, commits,
tags, and publishes to nuget.org. No human unless a gate trips.

Two gates stop it. `oasdiff` compares the schemas, and .NET package validation
(`make api-compat`) compares the C# API against the last published package.
A halted run does **not** commit the new schema, so every later run sees the
same diff and halts the same way until someone acts. That is deliberate, and
why the issues are deduped.

To release a breaking change, run the workflow from the Actions tab with
**bump: major** and **acknowledge_breaking: true**. Both are required together.

The version is passed to `dotnet pack` on the command line. The `.csproj`
holds `0.0.0-dev` and is never rewritten, so a release commit contains only
`openapi.json` and the generated code.

### When package validation stops a release

Kiota's output absorbs almost every additive schema change without breaking
callers: models are classes with settable properties, and query parameters are
properties on a class. One additive change is not absorbed. When an operation
that had no query parameters gains its first, its method signature changes
from `RequestConfiguration<DefaultQueryParameters>` to a new generated class.
Source that calls it still compiles, but a library compiled against the old
version gets `MissingMethodException`. Package validation reports it as
`CP0002` and the release files a `release-stuck` issue.

That is a binary break only, and not worth a major version. To accept it:

```bash
make fetch
make generate
make api-compat VERSION=0.0.0 API_COMPAT_FLAGS=-p:ApiCompatGenerateSuppressionFile=true
```

This writes `src/IncidentIo/CompatibilitySuppressions.xml`. Read it, and check
it lists only the expected members. Commit it on its own and discard the rest
(`git checkout openapi.json src/IncidentIo/Generated`), so the next sync still
sees the schema change, regenerates, and releases it. Suppressions stay valid after that release, because the project sets
`ApiCompatPermitUnnecessarySuppressions`.

Anything else package validation reports, such as a removed type or member, is
a real break: cut a major.

### Why the schema is rewritten before generation

Kiota has no naming options, so the schema copy is the main place to steer it.
`scripts/prepare_spec.py` changes names and doc
text, and removes parameters the client can't send. None of it changes what
goes over the wire, and `openapi.json` itself stays exactly as fetched. Each
pass has a count floor, so a schema or generator change that makes one stop
matching fails the release instead of quietly changing the public API.

- **Object query parameters are removed.** These are the list filters
  (`created_at[gte]=`). Kiota types them as a plain string and sends
  `created_at=<value>`, which the server doesn't read as a filter. The README
  documents sending filters with `WithUrl`.
- **Deprecated operations get a message.** Kiota emits `[Obsolete]` with an
  empty message unless `x-ms-deprecation` supplies one.
- **Path parameters become camelCase.** Otherwise the builder for
  `{alert_source_config_id}` is `WithAlert_source_config_ItemRequestBuilder`.
  Path segments can't be renamed in the schema, because Kiota builds the URL
  from them; `scripts/rename_identifiers.py` renames them in the output instead
  (see below).
- **Inline schemas move under `components/schemas`.** Kiota names an inline
  enum or object `Parent_snake_case_property`. As a component it takes the name
  `ParentPascalCaseProperty`. The name depends only on the parent and the
  property, so it doesn't change when the rest of the schema does.
- **Enum members become PascalCase** through `x-ms-enum`, with the wire value
  unchanged: `SplunkOnCall`, not `Splunk_on_call`.

After generation, `scripts/rename_identifiers.py` PascalCases the names Kiota
takes from URL path segments: `client.V2.AlertRoutes` rather than
`client.V2.Alert_routes`, with the folders and files to match. It only touches
identifiers that start with a capital letter. The URL templates and query
parameter names are lowercase strings, so the wire format is unchanged. It
fails on a name collision or if the count of renames drops below a floor.

All of these are names in the public API, so changing any of the rules after
the first release is a breaking change.

## First release checklist

1. **Create the trusted-publishing policy** on nuget.org, under the
   `incident-io` account that owns the package: repository owner
   `incident-io`, repository `sdk-net`, workflow file `sync.yml`, package
   `IncidentIo`. Its scope must allow **new packages and package versions**. A
   scope that only allows new versions rejects the first release, which
   creates the package. Renaming `sync.yml` later silently breaks publishing.
   The workflow names the account in the `NuGet/login` step (`user:`); change
   it there if the package moves to another account.
2. **Optionally reserve the `IncidentIo` prefix** by emailing
   account@nuget.org. It adds the verified badge and stops anyone else
   publishing under the prefix.
3. **Run the workflow once manually** with `dry_run: true` and confirm it gets
   as far as reporting a version. It only does work when the live schema
   differs from the committed one.
4. **Uncomment the `schedule:` block** at the top of
   `.github/workflows/sync.yml`. Nothing else enables the loop, and nothing
   checks that you did: until this happens the repo looks healthy and publishes
   nothing.

The first release is `v1.0.0`. Unlike crates.io, nuget.org creates the package
on the first trusted publish, so there is no manual publish step.

A trusted-publishing policy for a private repository is only temporarily
active for 7 days, and becomes permanent after its first successful publish.

## Keeping the loop alive

Everything that reports a problem here is a `failure()` hook, and a loop that
never runs never fails. Two ways it can go quiet:

- GitHub **disables a scheduled workflow after 60 days** with no repository
  activity, and emails only whoever last edited the cron. This repo's activity
  is its own release commits, which stop exactly when the schema stops
  changing.
- Someone reverts or never enables the cron.

Each successful run writes a line to its job summary saying what it decided, so
"when did this last sync?" is answerable from the Actions run list. If the run
list is empty for a week, the loop is off, not quiet.

## Upgrading Kiota or the .NET SDK

Both are pinned: Kiota in `.config/dotnet-tools.json`, the SDK in
`global.json`. A Kiota minor release can reshape the generated public API, and
a new SDK can bring analyzer warnings that `-warnaserror` turns into a halted
release. Dependabot is told to leave Kiota alone.

To upgrade Kiota:

1. Change the version in `.config/dotnet-tools.json`.
2. `make generate`, then read `git diff --stat` and the diff of a few models
   and request builders. Check the counts `prepare_spec.py` prints didn't
   collapse.
3. `make test`, and `make api-compat` to see whether the new output breaks the
   published API. If it does, the upgrade belongs in a major release.

The Kiota runtime packages (`Microsoft.Kiota.Bundle`) are ordinary
dependencies and are updated by Dependabot.
